# ATOM — data architecture

> **Status:** Accepted (living document)
> **Last updated:** 2026-10-24
> **Owner:** maintained by the `architect` agent

How the data is shaped, owned, searched and indexed, and how the migrations
and the Rust models stay in step.

The column-by-column schema is in
[`../database/schema.md`](../database/schema.md). The workflow for changing it
is in [`../database/migration-policy.md`](../database/migration-policy.md).
This document explains **why** the model looks like this.

---

## 1. The persistence model

PostgreSQL is the only datastore. There is no cache, no search service, no
object store and no second database.

```text
users ─────┬──► refresh_sessions        (rotation link, self-referencing)
           │
           ├──► notes                   (soft delete through `is_archived`)
           │
           └──► projects ──► tasks      (ownership inherited through the project)
```

| Table | Owning module | Purpose |
| ----- | ------------- | ------- |
| `users` | `users` | The account. The root of every ownership relation. |
| `refresh_sessions` | `auth` | One row per issued refresh token. Only the SHA-256 hash of the token is stored. |
| `notes` | `notes` | A personal, owned, searchable text record. |
| `projects` | `projects` | An owned container for tasks. |
| `tasks` | `tasks` | A unit of work inside a project. |

### 1.1 Conventions that hold everywhere

| Convention | Rule |
| ---------- | ---- |
| Primary key | `UUID`, generated by the application with `Uuid::new_v4()`. No sequential identifier is ever exposed. |
| Timestamp | `TIMESTAMPTZ` for every timestamp, rendered as RFC 3339 UTC. |
| Ownership | A non-null `UUID` foreign key to `users`, with an explicit `ON DELETE` behaviour. |
| Uniqueness | Enforced by the database, never by a check-then-insert in the application. |
| Controlled state | A PostgreSQL enum type, so an out-of-contract value cannot be persisted. |
| Length limits | A `CHECK` constraint that mirrors the validation in the service. |
| Index | One index per access path the API actually uses. |
| Mutation | `updated_at = NOW()` is set by the statement, never by the application. |

### 1.2 Deletion semantics

| Parent | Child | Behaviour |
| ------ | ----- | --------- |
| `users` | `notes`, `projects`, `refresh_sessions` | `ON DELETE CASCADE` |
| `projects` | `tasks` | `ON DELETE CASCADE` |
| `refresh_sessions` | `refresh_sessions` (`replaced_by_session_id`) | `ON DELETE SET NULL` |

Deleting a user therefore removes every note, every project, every task
inside those projects and every session. Deleting a project removes its
tasks. The product question behind the project cascade — delete or archive —
is open (Q1 in [`../project-truth.md`](../project-truth.md) §16) and is
recorded in [`../features/projects/specification.md`](../features/projects/specification.md).

## 2. The ownership model

**Every resource belongs to exactly one user.** Phase 1 is single-owner by
design; there is no sharing, no collaboration and no multi-tenancy.

The ownership rule is expressed in three places, and all three must agree:

1. **In the schema.** `notes.user_id`, `projects.user_id` and
   `refresh_sessions.user_id` are non-null foreign keys to `users(id)`.
   `tasks` has **no** `user_id` column: it inherits ownership from its
   project.
2. **In the repository.** Every statement that reads or writes user data
   carries the caller's `user_id` in a bound parameter. The task repository
   reaches the project with a join, so the predicate is `p.user_id = $n`.
3. **In the service.** The service turns "no row" into
   `AppError::NotFound`, so an inaccessible resource is reported as `404`,
   never `403`.

This is the decision recorded in
[`../decisions/ADR-0005-ownership-enforced-in-sql.md`](../decisions/ADR-0005-ownership-enforced-in-sql.md).

### 2.1 The task join

A task has no owner column, so every task statement reaches the project:

```sql
FROM tasks t
JOIN projects p ON p.id = t.project_id
WHERE t.id = $1 AND p.user_id = $2
```

The insert is the same idea in one statement, which makes it impossible to
attach a task to a project the caller does not own:

```sql
INSERT INTO tasks (id, project_id, title, ...)
SELECT $1, p.id, $4, ...
FROM projects p
WHERE p.id = $2 AND p.user_id = $3
```

The update and the delete use the same join in their `WHERE` clause
(`UPDATE … FROM projects p WHERE …` and `DELETE … USING projects p WHERE …`).

### 2.2 The one exception

`UserRepository::find_by_email` reads a private table without an owner
predicate. It looks the account up **by its identity** in order to
authenticate it, which is the one case where the identity is the thing being
looked up.

### 2.3 Widening the predicate later

A future team-membership model widens the predicate in the repository — from
`p.user_id = $n` to an `EXISTS` over a membership table — and leaves the
handler, the service and the DTOs untouched. That is the reason the
predicates are written as an explicit join or subquery rather than as a
helper the modules share.

## 3. The search design

### 3.1 Notes: a generated `tsvector`

The `notes` table carries a stored, generated column:

```sql
ALTER TABLE notes
    ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(to_tsvector('simple', COALESCE(title, '')), 'A') ||
        setweight(to_tsvector('simple', COALESCE(content, '')), 'B')
    ) STORED;

CREATE INDEX notes_search_vector_idx ON notes USING GIN (search_vector);
```

- It is **generated**, so it cannot drift from the columns it is derived from
  and the application never has to maintain it.
- It is **owned by the note row**, so a search result is restricted to the
  note's owner by construction: the ownership predicate and the search
  predicate are in the same statement.
- The title is weighted `A` and the content is weighted `B`, so a title match
  outranks a content match when the configuration is ever used for ranking.
  Phase 1 does not rank: the query is a plain match, and ranking and
  highlighting are open question Q4.
- The query is:

  ```sql
  AND search_vector @@ plainto_tsquery('simple', $3)
  ```

  `plainto_tsquery` treats the search term as a bag of words with no
  operators, so a client cannot inject a tsquery expression.
- **The clause lives in its own statement.** A listing with a search term and a
  listing without one are two statements, not one statement guarded by
  `($3::text IS NULL OR …)`. The guard was measured against the split: under a
  generic plan it hid the selectivity of the search from the planner, which
  then read the owner's whole active set and discarded 19 000 of 20 000 rows
  as a filter. With the split the planner intersects
  `notes_user_id_archived_idx` and `notes_search_vector_idx` in a `BitmapAnd`:
  **10.80 ms became 0.85 ms and 819 buffers became 21**, and the same change on
  the count took **9.93 ms to 1.33 ms**. That is why `src/notes/repository.rs`
  writes the four statements out as constants instead of assembling one.

### 3.2 Why the `simple` configuration

`to_tsvector('simple', …)` is used deliberately, and it is the same
configuration in the column and in the query.

- **ATOM notes are technical.** They contain identifiers, file names, error
  codes and code fragments.
- **`simple` does not stem.** A stemmer would fold `config` and
  `configuration` together, and would also fold away the distinction between
  technical tokens that merely look like words.
- **`simple` does not apply language-specific tokenisation.** A note that
  mentions `Ünicode` or `rust-analyzer` keeps those tokens intact.
- **The behaviour is predictable and testable**, which is what the Phase 1
  requirement asks for.

The cost of `simple` is that a search for "running" does not match "run". The
alternative — a language-specific configuration — would make the behaviour of
a technical note depend on a language that was never declared.

### 3.3 Projects: a substring match

Projects have no `tsvector`. The optional search on
`GET /api/v1/projects` is a case-insensitive substring match:

```sql
AND (name ILIKE '%' || $2 || '%'
     OR description ILIKE '%' || $2 || '%')
```

It is a deliberate difference from the notes search: a project is a short
label, and a substring match is enough to find one. The trade-off is that a
leading wildcard cannot use a B-tree index, so the project search is a scan
within the owner's rows. Like the notes search, the clause is in its own
statement rather than guarded by `($2::text IS NULL OR …)`, so the listing
without a term stays on `projects_user_id_created_at_idx`.

### 3.4 Tasks: no search

Tasks are filtered by `status` and `priority`, both of which are indexed.
There is no free-text search over tasks.

## 4. The index strategy

Every index exists because a statement in a repository needs it. There is no
index without a query, and no query without an index unless the table is
tiny.

| Index | Table | Serves |
| ----- | ----- | ------ |
| `users_email_unique_idx` (unique) | `users` | `find_by_email`; the uniqueness of the normalized address. |
| `refresh_sessions_token_hash_unique_idx` (unique) | `refresh_sessions` | `find_by_token_hash`; one row per token. |
| `refresh_sessions_user_id_idx` | `refresh_sessions` | `revoke_all_for_user`. |
| `refresh_sessions_active_idx` (partial, `WHERE revoked_at IS NULL`) | `refresh_sessions` | The active-session query. |
| `notes_user_id_created_at_idx` | `notes` | The primary listing path: the owner's notes, newest first. |
| `notes_user_id_archived_idx` | `notes` | The active/archived filter. |
| `notes_search_vector_idx` (GIN) | `notes` | The full-text search. |
| `projects_user_id_created_at_idx` | `projects` | The primary listing path. |
| `tasks_project_id_position_idx` | `tasks` | The task listing, ordered by `position`. |
| `tasks_project_id_status_idx` | `tasks` | The status filter. |
| `tasks_project_id_priority_idx` | `tasks` | The priority filter. |

The primary keys of `users`, `refresh_sessions`, `notes`, `projects` and
`tasks` are indexed by their `PRIMARY KEY` constraint.

Three gaps are worth naming:

- The **project search** uses a leading wildcard and therefore has no
  supporting index. It scans the owner's rows, which is bounded by the
  owner's own project count.
- The **note search** uses a GIN index on `search_vector` alone, so the index
  itself is not restricted to the owner. The planner intersects it with
  `notes_user_id_archived_idx` in a `BitmapAnd` — measured at 0.85 ms and 21
  buffers over 20 000 owner rows — so both predicates are served by an index
  and neither is a post-filter over the owner's whole set. A *partial* GIN
  index keyed on the owner would be faster still, but `user_id` cannot appear
  in an index on a generated `tsvector` column, and a per-owner index is not
  worth the write cost at this scale.
- The **expired-session cleanup** filters on `expires_at`, for which there is
  no index. The background task in `src/main.rs` calls
  `RefreshSessionRepository::delete_expired` every hour, so the scan runs
  periodically over the whole table.

## 5. From migration to Rust model

The migrations are the source of truth for the schema, and the persistence
layer is written by hand against it. The two therefore change together.

| Schema object | Rust counterpart | Where it lives |
| ------------- | ---------------- | -------------- |
| `users` table | `struct User` with `#[derive(sqlx::FromRow)]` | `src/users/models.rs` |
| `users` table | `UserRepository` | `src/users/repository.rs` |
| `refresh_sessions` table | `struct RefreshSession` | `src/auth/models.rs` |
| `notes` table | `struct Note` | `src/notes/models.rs` |
| `projects` table | `struct Project` | `src/projects/models.rs` |
| `tasks` table | `struct Task` | `src/tasks/models.rs` |
| `task_status` enum | `enum TaskStatus` with `#[derive(sqlx::Type)]`, `type_name = "task_status"`, `rename_all = "snake_case"` | `src/tasks/models.rs` |
| `task_priority` enum | `enum TaskPriority`, the same way | `src/tasks/models.rs` |
| A `CHECK` constraint | A validation function in the service that answers `422` with a field name | `src/*/service.rs` |
| A column | A field on the model, the column in every `SELECT` and `INSERT`, and the field on the DTO when it is public | `src/*/models.rs`, `src/*/repository.rs`, `src/*/dto.rs` |

Two rules make this work:

- **The column list is written out.** Every statement spells out its columns
  rather than using `SELECT *`, so a new column is a visible diff in every
  statement that has to carry it.
- **The persistence model never leaves the service layer.** `Note`,
  `Project`, `Task` and `User` carry the persistence shape, including
  `user_id` and `password_hash`. The public shapes — `NoteResponse`,
  `ProjectResponse`, `TaskResponse`, `UserResponse` — are separate types
  with an explicit `From<Model>` conversion. The model is consumed rather
  than borrowed, so the strings of a listed page move into the response
  instead of being copied. `UserResponse` therefore cannot leak the password
  hash.

The migrations are embedded in the binary with `sqlx::migrate!("./migrations")`
and are applied at start-up, before the socket is bound.

## 6. Behaviours that live in the database

Three behaviours are worth calling out, because they are implemented in the
database rather than in the Rust code:

| Behaviour | Where it lives | Why |
| --------- | -------------- | --- |
| `search_vector` is recomputed on every write | The generated column in `migrations/0002_notes.sql` | The index can never disagree with the text it indexes. |
| `completed_at` follows `status` | The `UPDATE` statement in `src/tasks/repository.rs` plus the `tasks_completion_consistency_chk` constraint | The timestamp is set when the status becomes `done` and cleared when it leaves `done`; the constraint refuses any other combination. |
| `updated_at` follows the write | `updated_at = NOW()` in every `UPDATE` statement | The application never computes a timestamp for a write. |

## 7. Transaction boundaries

**There is no explicit transaction in the Phase 1 request path.** Each
repository method runs one statement, and each statement is atomic on its own.

The one place where two writes belong together is the refresh-token rotation
in `auth::service::refresh`:

1. `RefreshSessionRepository::insert` inserts the replacement session. It
   comes first, because `replaced_by_session_id` is a foreign key to it.
2. `RefreshSessionRepository::claim` revokes the presented session and
   records `replaced_by_session_id`. The statement only matches a session
   that is still active, so two concurrent requests carrying the same token
   cannot both succeed: the loser sees zero affected rows and is treated as
   a reuse.

These two statements are **not** wrapped in a transaction. The consequence is
bounded: if the process dies between them, the old session is still valid
and the new one exists, so the next refresh with the old token succeeds and
the rotation is retried. The opposite order — claiming first — would leave a
caller with no usable session at all. The current order fails safe.

A transaction is therefore a known, deliberate absence rather than an
oversight. The migration policy in
[`../database/migration-policy.md`](../database/migration-policy.md) already
requires an explicit transaction for any future multi-step write that cannot
fail safe. The requirement it implements is in
[`../project-truth.md`](../project-truth.md) §12, which allows an exception
when an accepted ADR records that the ordering fails safe, and
[`../decisions/ADR-0003-auth-token-design.md`](../decisions/ADR-0003-auth-token-design.md)
is that ADR.

### 7.1 The deadline is preserved by the rotation

The replacement session **inherits the original `expires_at`**. The rotation
does not recompute the expiry from the current time, so the absolute lifetime
of a session is measured from the moment it was created, and a client that
refreshes every hour does not extend its own session indefinitely.

The property matters because the absolute lifetime is the upper bound on the
value of a stolen refresh token. A rotation that recomputed the deadline
would silently turn the absolute lifetime into a sliding one: the only bound
would be "as long as the thief keeps refreshing", and the lifetime recorded
in [`../decisions/ADR-0003-auth-token-design.md`](../decisions/ADR-0003-auth-token-design.md)
would no longer be a bound at all.

The defect that broke this property, and its resolution, are recorded as
`KI-015` in [`../engineering/known-issues.md`](../engineering/known-issues.md).

> `embeddings` (§11.6 of [`../database/schema.md`](../database/schema.md)) is the
> only table here that is still proposed. All of them are the schema implied by
> the **accepted** Phase 2 requirements
> ([`../project-truth.md`](../project-truth.md) §18), and they are described
> column by column in [`../database/schema.md`](../database/schema.md) §11 —
> which is the authority for the physical definition. This section records only
> what the *data architecture* has to say about them: how the conventions of §1
> carry over, and where Phase 2 departs from them.

*The heading is unnumbered on purpose:* §7 is cited by number from
[`../project-truth.md`](../project-truth.md) §12, so renumbering it would
repoint that reference.

### The migrations, and the number of tables

Three migrations, one per feature, in this order. The numbers are fixed by
[`../database/schema.md`](../database/schema.md) §11.8 and the append-only rule
of §5 above applies unchanged: each lands with its Rust models, its repository
statements, its DTOs and its seeder extension in the same change, and none edits
a migration that has been applied.

| Migration | Creates | Requirements |
| --------- | ------- | ------------ |
| `0004_expense_claims.sql` | `expense_claim_status`, `expense_claims`, `expense_items`, with their constraints and indexes | `REIMB-R01`…`R10` |
| `0005_job_applications.sql` | `job_application_status`, `application_event_kind`, `companies`, `job_applications`, `application_events`, with their constraints and indexes | `JOB-R01`…`R09` |
| `0006_embeddings.sql` | `embeddings`, with its constraints and indexes | `ML-R01`…`R09` |

Six tables and three enum types. No migration creates a PostgreSQL extension:
`REAL[]` is a built-in type, and the reason the `vector` extension is not used is
recorded in [`../decisions/ADR-0008-local-pure-rust-ml.md`](../decisions/ADR-0008-local-pure-rust-ml.md).

### The conventions that do not change

- **Primary keys** are still application-generated `UUID`s; **timestamps** are
  still `TIMESTAMPTZ`, with two `DATE` columns for calendar days
  (`expense_items.incurred_on`, `job_applications.applied_on`) because a day is
  not an instant. **Length limits** are still mirrored by a `CHECK`. **Deletion**
  is still explicit in the schema, through an `ON DELETE` behaviour on every
  foreign key.
- **Uniqueness is still enforced by the database**, never by a check-then-insert:
  `(user_id, lower(name))` on `companies` and
  `(user_id, source_type, source_id, model_id)` on `embeddings` are the two new
  examples.
- **Controlled state is still refused by the database**: the claim status, the
  application stage and the event kind are native enum types, so an
  out-of-contract value cannot be persisted. The *transition* between two legal
  values stays a service rule, because a `CHECK` sees one row and cannot see the
  previous state.

### The ownership model, unchanged

Every Phase 2 table carries `user_id`, and every statement carries it as a bound
parameter — the rule of [`../decisions/ADR-0005-ownership-enforced-in-sql.md`](../decisions/ADR-0005-ownership-enforced-in-sql.md)
and of §2 above. The difference from Phase 1 is narrow and deliberate: Phase 1
has exactly one table without the column — `tasks` — and **no Phase 2 table
does**. `expense_items` and `application_events` are children, and they carry the
owner themselves, so the child's predicate needs no join and a cross-owner child
row is made unrepresentable by a composite foreign key rather than by a service
check.

Two links the database cannot constrain on the caller's side, and what replaces
the constraint:

| Link | Why SQL cannot prove it | What does |
| ---- | ----------------------- | --------- |
| `expense_claims.project_id` | The column is nullable with `ON DELETE SET NULL`, so it is not part of a composite key to the project's owner | One owner-scoped read of `projects` before the write; a foreign id is `404` |
| `job_applications.next_action_task_id` | `tasks` has no `user_id`, so there is nothing to reference | The same read through the `tasks → projects` join of §2.1; a foreign id is `404` |

An inaccessible row is still `404`, never `403`. That is unchanged, and it is
the reason the two links above are verified by the service rather than surfaced
as a constraint violation.

### The polymorphic `embeddings.source_id`

`embeddings.source_id` points at either a note or an application, chosen by
`source_type`, so it can carry **no foreign key** — PostgreSQL cannot reference
two tables from one column. The trade-off and its price are recorded in
[`../decisions/ADR-0008-local-pure-rust-ml.md`](../decisions/ADR-0008-local-pure-rust-ml.md)
and in [`../database/schema.md`](../database/schema.md) §11.6; the consequence
for this document is one **cleanup rule that has no equivalent in Phase 1**:

- **The delete that removes a source removes its embeddings in the same
  transaction.** A note delete and an application delete therefore become
  multi-statement transactions (below).
- **The reindex is the backstop.** `POST /api/v1/ml/reindex` deletes the caller's
  embeddings whose source no longer exists, so a delete path that forgot the
  rule leaves a leak of storage rather than a leak of data — the row is
  unreachable through any owner-scoped query.
- **The read side never relies on the row existing.** Every embedding read
  filters `user_id` and `source_type` first, so a stale `source_id` cannot
  return another account's note.
- **The write is in the same transaction as the source row**, so an embedding
  cannot be inserted for a source whose insert rolled back.

The module edge this creates — `notes` and `job_applications` calling one SQL
function in `ml`, and nothing calling `MlService` — is fixed in
[`module-boundaries.md`](module-boundaries.md).

### The money rule

Four columns carry money: `expense_claims.total_amount`, `expense_items.amount`,
`job_applications.salary_min` and `job_applications.salary_max`. All four are
`NUMERIC(19,4)`, and the wire form is a **string** with exactly four decimal
places. The decision, and the reasons no floating-point type may appear on the
path, are in [`../decisions/ADR-0007-money-representation.md`](../decisions/ADR-0007-money-representation.md).

Three consequences for the persistence layer, plus one constraint the
implementing change had to satisfy before `0004` was written:

1. **Money crosses the repository boundary as a `String`**, selected with an
   explicit `::text` cast. No `numeric` reaches Rust as anything else.
2. **The arithmetic happens in PostgreSQL** — `SUM(amount)` for the claim total,
   `CHECK (salary_min <= salary_max)` for the range — never in Rust.
3. **The type that parses and renders it is shared by both features**, so the
   four decimals have one home. Its placement is decided in
   [`module-boundaries.md`](module-boundaries.md) under the `money` module.
4. **`sqlx` has no enabled feature that can decode `NUMERIC` today** — no
   `rust_decimal`, no `bigdecimal`
   ([`../database/schema.md`](../database/schema.md) §11.8, item 1). `0004` must
   either add one (a dependency change with its recorded reason) or keep the
   `::text` cast on every money read. What it must not do is decode through
   `f64`.

### The first explicit transactions in a request path

§7 above records that **Phase 1 has no explicit transaction in the request
path**, and that statement stays true for Phase 1. Phase 2 introduces the first
ones, because four operations have an invariant that spans two statements:

| Operation | Statements that must commit together |
| --------- | ------------------------------------ |
| Insert, update or delete a line item | The item write and the `total_amount` recomputation (`REIMB-R03`) |
| Submit, decide or pay a claim | The status change and the lifecycle timestamps |
| Change an application's stage | `SELECT … FOR UPDATE`, `ensure_transition`, and the `UPDATE` |
| Delete a note or an application | The delete and the embeddings it owns |

The pattern is the same in all four: one service method opens the transaction,
the repository functions take the caller's connection or transaction, and a
refused rule rolls the whole thing back. A reindex is the deliberate exception —
it is per-row and idempotent, so one transaction per row rather than one for the
run, because an interrupted run is simply run again.
