# Authentication — architecture

> **Status:** Accepted (living document)
> **Last updated:** 2026-10-22
> **Owner:** maintained by the `docs` agent
> **Feature:** [`ATOM-FEAT-AUTH-001`](specification.md)

How the authentication feature is built. The public contract is in
[`api.md`](api.md); the agreed requirements are in
[`specification.md`](specification.md).

## 1. Responsibilities

| Module | Responsibility |
| ------ | -------------- |
| `src/api/middleware.rs` | Extracts the caller from the `Authorization` header (`AuthUser`), determines the client address (`ClientIp`), and enforces the rate limit (`enforce_rate_limit`). |
| `src/auth/handlers.rs` | HTTP only: extraction, rate limiting, status codes, response serialization. |
| `src/auth/service.rs` | The authentication use cases: registration, login, refresh rotation, logout, session revocation, bearer verification. Owns the rules, not the transport. The client-facing wording comes from the message catalogue, which the service holds. |
| `src/auth/password.rs` | Argon2id hashing and verification with configurable cost parameters. |
| `src/auth/token.rs` | Access-token issuing and verification (HS256 JWT), opaque refresh-token generation and hashing. |
| `src/auth/repository.rs` | Persistence for refresh sessions. |
| `src/auth/models.rs` | The `RefreshSession` persistence shape. |
| `src/auth/dto.rs` | The public request and response contracts of the feature. |
| `src/users/service.rs` | User use cases and the validation rules that are not tied to one request: `normalize_email`, `validate_email`, `validate_password`, `validate_display_name`, and the safe public representation. The rules take the message catalogue, and the password lengths come from the configured policy (`auth.password.min_length` and `auth.password.max_length`). |
| `src/users/repository.rs` | User persistence. Maps the unique-violation SQLSTATE to a conflict and the check-violation SQLSTATE to a validation failure. |
| `src/users/models.rs` | The `User` persistence shape. |
| `src/users/dto.rs` | `UserResponse` and `RegisterRequest`. |

The layering is fixed and matches every other feature: handlers → service →
repository → PostgreSQL. A handler never touches the database and a
repository never makes a business decision.

## 2. Interfaces

The feature is entered in exactly two ways.

### 2.1 The `AuthUser` extractor

```rust
pub struct AuthUser {
    pub user_id: Uuid,
    pub email: String,
}
```

`AuthUser` implements `FromRequestParts<AppState>`. A handler that takes it
as an argument cannot be reached without a credential. The extractor:

1. reads the `Authorization` header, and rejects a missing or non-UTF-8
   header with `401`;
2. strips a case-insensitive `Bearer ` prefix and rejects an empty token;
3. calls `AuthService::authenticate_bearer`, which decodes the token, loads
   the user and rejects a disabled account.

The `user_id` in the extractor is the **only** identity a handler ever uses.
Nothing in the request body, query string or path can override it.

### 2.2 The `AuthService`

| Method | Purpose |
| ------ | ------- |
| `register(request, meta)` | Validates, hashes, creates the user, issues the first token pair. |
| `login(request, meta)` | Verifies the credentials, issues a token pair. |
| `refresh(refresh_token, meta)` | Rotates the session and issues a new token pair. |
| `logout(user_id, refresh_token)` | Revokes the caller's own session. |
| `revoke_all_sessions(user_id)` | Revokes every active session of a user. |
| `prune_expired_sessions(grace)` | Deletes the sessions that expired more than `grace` ago. |
| `current_user(user_id)` | Returns the caller's public representation. |
| `authenticate_bearer(token)` | Validates an access token and returns the user. |

`AuthService` is built once in `AppState::new` and shared behind an `Arc`.
It holds the `UserService`, the `UserRepository`, the
`RefreshSessionRepository`, the `TokenService`, the `PasswordHasher`, the
message catalogue and the refresh-token lifetime. The timing-equalisation hash
belongs to the `PasswordHasher`: it is a hash of an unguessable value, computed
with the configured Argon2 parameters, used to equalise the time a login takes
when the address does not exist.

## 3. Data ownership

| Table | Owner column | Meaning |
| ----- | ------------ | ------- |
| `users` | — | The account itself. `id` is the UUID generated by the application. |
| `refresh_sessions` | `user_id` → `users (id) ON DELETE CASCADE` | One row per issued refresh token. Deleting a user deletes the sessions. |

The feature owns both tables. Nothing else in the system writes to them.

The schema is described in full in
[`schema.md`](../../database/schema.md); the relevant tables were introduced
by `migrations/0001_users_and_sessions.sql`.

## 4. Invariants

These hold at every point in the request path, and each of them is backed by
code and, where it matters, by a database constraint.

| # | Invariant | Enforced by |
| - | --------- | ----------- |
| 1 | A stored email is trimmed and lower-cased. | `normalize_email` in the service, plus the `users_email_normalized_chk` check constraint. The two cannot drift. |
| 2 | An email address identifies at most one account. | The `users_email_unique_idx` unique index. The repository maps SQLSTATE `23505` to `409 conflict`, so there is no check-then-insert race. |
| 3 | A password is never stored in plaintext and never leaves the process. | `PasswordHasher::hash` produces a PHC-formatted Argon2id string; the plain password is never bound to a query, logged or returned. |
| 4 | A refresh token is never stored in recoverable form. | `hash_refresh_token` (SHA-256, hex) is the only value written to `token_hash`. The unique index `refresh_sessions_token_hash_unique_idx` prevents a duplicate. |
| 5 | A refresh token is used at most once. | `refresh` claims the presented session with an atomic update and inserts a replacement in the same call; `replaced_by_session_id` records the link. A claim that matches no row is treated as a reuse. |
| 6 | Presenting a revoked refresh token destroys every session of that user. | `refresh` calls `revoke_all_for_user` before returning the error, both for a token that is already revoked and for a concurrent rotation that lost the claim. |
| 7 | A caller can only revoke its own session. | `logout` compares `session.user_id` with the authenticated `user_id` and returns `403` on a mismatch. |
| 8 | The `Authorization` header is the only source of identity. | The `AuthUser` extractor; no other extractor reads an identity from the request. |
| 9 | A failed login is indistinguishable from an unknown account. | One constant message (`GENERIC_LOGIN_FAILURE`) for both cases, plus a dummy Argon2 verification when the address is unknown. |
| 10 | An access token is only accepted with the right issuer, audience, signature and expiry. | `TokenService::decode_access_token` validates the algorithm, the issuer, the audience and the required claims `exp`, `sub`, `iss`, `aud`, with 30 seconds of clock-skew leeway. |
| 11 | The signing secret and the database URL never appear in a log. | `AuthSettings` and `DatabaseSettings` implement `Debug` with the secret fields replaced by `[REDACTED]`. |
| 12 | An inactive account cannot authenticate or refresh. | `authenticate_bearer` and `refresh` both check `user.is_active` and return `403`. |

## 5. Error handling

Every failure is an [`AppError`](../../api/error-contract.md), and every
`AppError` renders the same envelope. The feature produces:

| Situation | Error | Status |
| --------- | ----- | ------ |
| Invalid email, weak password, invalid display name | `validation_failed` with one `FieldViolation` per problem | `422` |
| Email already registered | `conflict` | `409` |
| Wrong password, unknown email, unknown/expired/reused refresh token, invalid access token | `unauthorized` | `401` |
| Disabled account | `forbidden` | `403` |
| Logout with a token belonging to another user | `forbidden` | `403` |
| Rate limit exceeded | `rate_limited`, with a `retry-after` header | `429` |
| Database failure | `database_error` | `500` |

The driver message of a database failure is neither logged nor returned:
`AppError::body` replaces the detail of the `Database` and `Internal`
variants with a fixed sentence, and the log line carries only the SQLSTATE
and the error kind. A `CHECK` violation is mapped to a `422` in
`src/users/repository.rs` before it can reach the log at all.

## 6. The security boundary

```text
                    ┌──────────────────────────────────────┐
  anonymous  ─────► │  POST /auth/register                 │
                    │  POST /auth/login                    │
                    │  POST /auth/refresh                  │  public
                    ├──────────────────────────────────────┤
  bearer token ───► │  POST /auth/logout                   │
                    │  GET  /auth/me                       │
                    │  every /notes, /projects, /tasks route│  authenticated
                    └──────────────────────────────────────┘
```

- The public side is the three credential endpoints. They accept an email
  address and a password, and they are rate limited.
- The authenticated side requires a valid access token for an active
  account. The extractor resolves the token to a `user_id`, and everything
  downstream is scoped by it.
- The rate-limit key is the connection's peer address, taken from
  `ConnectInfo`. `X-Forwarded-For` is deliberately ignored, because a
  client-controlled header would let a caller forge the key. When the server
  was not started with connect information, all callers share one bucket.
- The `logout` endpoint is the one place where a caller acts on a session
  that is not its own; that is explicitly refused with `403`.

## 7. The request path

### 7.1 Registration

```text
POST /api/v1/auth/register
  │
  ├─ api::router           cors → trace → body limit → request id (set, propagate)
  │                        → timeout → catch_panic → route
  ├─ auth::handlers::register
  │    ├─ enforce_rate_limit(state, peer)            429 on excess
  │    └─ meta(&headers, peer)                       user-agent, ip
  ├─ auth::service::AuthService::register
  │    ├─ validate_email      → 422
  │    ├─ validate_password   → 422
  │    ├─ validate_display_name → 422
  │    ├─ PasswordHasher::hash                        Argon2id, 16-byte salt
  │    ├─ users::service::UserService::create_user
  │    │    └─ users::repository::UserRepository::insert
  │    │         INSERT INTO users (...) VALUES ($1..$4) RETURNING ...
  │    │         SQLSTATE 23505 → 409 conflict
  │    └─ issue_token_pair
  │         ├─ generate_refresh_token                32 random bytes, base64url
  │         ├─ auth::repository::RefreshSessionRepository::insert
  │         │    INSERT INTO refresh_sessions (...) VALUES ($1..$6) RETURNING ...
  │         └─ TokenService::issue_access_token      HS256 JWT
  └─ 201 Created, AuthResponse
```

### 7.2 Login

```text
POST /api/v1/auth/login
  ├─ enforce_rate_limit                              429 on excess
  └─ AuthService::login
       ├─ normalize_email
       ├─ UserRepository::find_by_email              SELECT ... WHERE email = $1
       ├─ unknown address → dummy Argon2 verify → 401 (generic message)
       ├─ PasswordHasher::verify                      false → 401 (generic message)
       ├─ !user.is_active → 403
       └─ issue_token_pair                            (as above)
```

### 7.3 Refresh

```text
POST /api/v1/auth/refresh
  ├─ enforce_rate_limit                              429 on excess
  └─ AuthService::refresh
       ├─ hash_refresh_token
       ├─ RefreshSessionRepository::find_by_token_hash
       ├─ revoked_at IS NOT NULL → revoke_all_for_user → 401
       ├─ !is_usable_at(now)        → 401 (expired)
       ├─ UserRepository::find_by_id → missing → 401
       ├─ !user.is_active           → revoke_all_for_user → 403
       ├─ RefreshSessionRepository::insert            the replacement session
       ├─ RefreshSessionRepository::claim(id, user_id, new_session_id)
       │    the claim is atomic; a claim that matches no row means the token
       │    was rotated concurrently → revoke_all_for_user → 401
       └─ TokenService::issue_access_token
```

### 7.4 Authenticated request

```text
GET /api/v1/notes  (or any private route)
  ├─ api::router layers
  ├─ api::middleware::AuthUser
  │    ├─ read Authorization: Bearer <token>          missing → 401
  │    └─ AuthService::authenticate_bearer
  │         ├─ TokenService::decode_access_token      any failure → 401
  │         ├─ Uuid::parse_str(claims.sub)            failure → 401
  │         ├─ UserRepository::find_by_id             missing → 401
  │         └─ !user.is_active                        → 403
  └─ handler → service → repository → SQL, every query scoped by user.user_id
```

## 10. Limitations of this design

- **The dummy hash is derived from the configured cost parameters.**
  `PasswordHasher::new` computes it once with the same `Argon2Params` the
  real hashes use, so verifying against it costs exactly what verifying
  against a stored password costs. The constant `DUMMY_HASH` in
  `src/auth/password.rs` is only the fallback used if that computation
  fails, which can only happen when the configured Argon2 parameters are
  rejected — and `Config` already refuses to start with invalid parameters,
  so the fallback is a belt-and-braces guard rather than a reachable state.
- **Rotation is not atomic across two statements.** The replacement session
  is inserted and the old session is claimed by two separate statements. A
  crash between them leaves the old session valid, so the next refresh with
  it succeeds and the rotation is retried; it does not create a reusable
  token, because the claim refuses to match a session that is already
  revoked.
- **The rate limiter fails open on a poisoned lock.** `RateLimiter::check`
  recovers the inner value of a poisoned mutex instead of panicking. This
  favours availability over strict enforcement.
- **Access tokens are not revocable.** A leaked access token is valid until it
  expires, even if the session it belongs to is revoked.
- **There is no per-session revocation of access tokens** and no `jti`
  blocklist, so the `jti` claim is currently unused.
